# Citation idempotence re-run reports false repairs until the pass commits

## Location

- `goc/templates/skills/refine-deck/reference.md` — § "Citation anchor check",
  the **Close the step by re-running it** paragraph. Mirrored to consumers at
  `.claude/skills/refine-deck/reference.md`, `.codex/skills/…`,
  `claude-plugin/skills/…`, `codex-plugin/skills/…`, `openclaw-plugin/skills/…`.
- `goc/templates/skills/refine-deck/SKILL.md` — § "Defunct file:line
  citations", the closing sentence of the condensed recipe.

## What's broken

The recipe ends with an idempotence check, and states the order as apply →
re-run:

> **Close the step by re-running it.** After applying the rewrites, run the
> decision phase again over the cards just written and assert it proposes
> ZERO further repairs.

The commit is never mentioned. But the anchor walk one section above is
defined over committed history:

> list `git log --follow --format=%H -- <deck>/<card>/README.md` oldest to
> newest, read the README at each commit, and take the newest commit at which
> the cite token turns from absent to present

An uncommitted rewrite is not in `git log`, so the walk cannot see it. For a
cite the pass has just written, the newest absent→present transition is
whatever the *previous* one was — and on a renumbering pass that is routinely
a **retired occurrence**: the number the card used to carry for a different
cite, before an earlier pass moved that cite somewhere else. The walk anchors
the fresh cite on the retired occurrence's text, finds that text elsewhere in
HEAD, and proposes moving a correct cite onto it.

The passes manufacture the shape as a matter of course. Each pass renumbers
cites within a narrow band of one file, so a repaired cite routinely lands on
a number a sibling held one or two passes ago.

**This is not the collision the 2026-09-14 fix addressed.** That fix closed
two doors and both are already shut here:

- *Substring collision* — presence is set membership over extracted tokens, so
  no range that merely spells the number can claim it.
- *Convergence* — a token at two or more in-scope occurrences is declined, and
  each cite below occurs exactly **once** in its card.

The colliding occurrence is in the card's **past**. A count of current
occurrences cannot see it, which is why every one of these passes the
ambiguous-occurrence guard cleanly.

## Empirical evidence

The 2026-09-21 hygiene pass repaired 269 cites across 92 cards, then ran the
idempotence check twice over the identical repair set — once before committing
and once after:

```
before the commit : {'decline': 490, 'current': 219, 'repair': 269}  (round 1)
                    {'decline': 756, 'current': 219, 'repair':   3}  (re-run)
after  the commit : {'decline': 492, 'current': 486, 'repair':   0}  (re-run)
```

The three are false. Each names code HEAD holds at exactly the cited number:

| Card | Cite | HEAD holds at that line | Re-run would move it to |
|---|---|---|---|
| `draft-gating-is-opt-in-per-surface-and-new-verbs-keep-missing-it` | `engine.py:2695` | `if card_is_draft(card) and not include_drafts:` | `:2780`, `def live_impeded(` |
| `misspelled-workflow-config-boolean-silently-turns-the-feature-on` | `goc/engine.py:5135` | `def _coerce_config_bool(value, *, default: bool) -> bool:` | `:5238`, a *call site* of that function |
| `claim-push-calls-any-failed-rebase-a-claim-race-and-advises-a-reset` | `goc/engine.py:5283` | `if check.returncode == 1:` | `:5386`, `worker = fm.get("worker")` |

Each token was present at an older commit, absent at the pass's input state,
and written fresh by the pass — confirming the anchor came from a retired
occurrence and not from the cite being repaired:

```
engine.py:2695      @f290f5f7 present=1   @HEAD~1 present=0
goc/engine.py:5283  @e8449764 present=1   @HEAD~1 present=0
goc/engine.py:5135  @29504aec present=3   @HEAD~1 present=0
```

`reproduce.py` generalizes this past the three cites the pass happened to
touch. It withholds the writing commit from the walk — exactly what the
pre-commit re-run sees — and censuses the whole live deck:

```
open/active cards scanned                 : 208
single-occurrence in-scope cites anchored  : 371

cites whose anchor is decided by a RETIRED occurrence when the
writing commit is withheld [...]

  claim-push-calls-any-failed-rebase-a-claim-race-and-advises-a-reset
      cite goc/engine.py:5283  withheld-anchor e8449764a -> would rewrite to :5386
      retired occurrence's text: 'worker = fm.get("worker")'
      full-history anchor 9085ef049 verdicts: current
  [...19 further rows...]

false repairs the pre-commit re-run proposes: 3
```

**21 cites across 19 cards carry the shape.** Three are live false repairs —
the ones this pass wrote. The other 18 are latent: their full-history anchor
also reads defunct, so they are declined or repaired on other grounds today,
and each converts into a false repair on the next pre-commit re-run that
happens to write it.

## Why it matters

The re-run is the *only* thing standing between this recipe and silently
wrong cites. Its own predecessor card says so:

> The colliding-anchor class above was found by exactly this re-run and by
> nothing else; a pass that had followed the recipe as written would have
> reported three successful repairs and left no trace of the three correct
> cites it moved.

So the check is load-bearing, and it is order-dependent in a way nothing
states. A pass following the shipped text literally — apply, re-run, then
commit — reads three well-formed proposals and has no rule that refuses them:
real anchor, unique match, confident rewrite. The recipe's own instruction for
a non-empty second round ("a recipe defect to file, not more rewrites to
apply") is what saved these three, and that instruction only holds if the pass
resists proposals that look exactly like the repairs it just made correctly.

The failure is also self-concealing in the usual way. Applying the three would
move correct cites onto unrelated code, and the *next* pass would then verdict
the wreck `current`, because by then the bad number has a committed anchor of
its own.

## Fix

The cheap and correct fix is ordering: **commit the rewrites, then re-run**.
The walk is defined over committed history, so committing first is what makes
its input match its definition — and the measurement above shows it converges
immediately (0 repairs, 486 current). The reference's re-run paragraph and
`SKILL.md`'s condensed step should both say so, and the residue table should
name the retired-occurrence shape so a pass that meets one out of order reads
it as a known decline.

A second path exists and is worth recording so it is rejected deliberately
rather than by omission: teach the walk to treat the **uncommitted working-tree
README as the newest version**, so a fresh rewrite anchors on itself and the
re-run works at any point. That is strictly more general — it also fixes a pass
that cannot commit (a dirty index, a shared-main collision per the repo's
parallel-agent rules) — but it is a change to the walk's definition rather than
to one sentence, and it makes the anchor depend on uncommitted state, which is
the property the 2026-08-17 card removed when it moved off the creating-commit
anchor.

Filed at `human_gate: none` by an autonomous pass with no human in the loop;
the ordering fix is the recommended path and is a one-sentence documentation
change. A later reader who wants the walk-level fix instead should raise the
gate and take it deliberately.
