# The queue view says nothing when it has nothing to say

## Location

Two sites, one behaviour:

- `goc/engine.py:3104-3105` — `render_table` returns the empty string
  for an empty card list, before it emits any header:

  ```python
  def render_table(
      cards: list[Card],
      ...
  ) -> str:
      if not cards:
          return ""
  ```

- `goc/engine.py:3949-3951` — `_cmd_default`'s non-JSON, non-board arm
  drops the print entirely when every part is falsy:

  ```python
  lines = [part for part in (active_notice, out, leverage) if part]
  if lines:
      print("\n".join(lines))
  ```

## What's broken

A zero-match query on the default table view produces **no output at
all** and exits 0. The other three read surfaces in the same command
family all announce the empty set:

| Surface | Zero-match output |
|---|---|
| `goc triage` (`engine.py:6340-6342`) | `No parked cards (gate ≠ none).` |
| `goc --json` (`render_json`) | `[]` |
| `goc --board` (`render_board`) | the column header row |
| **`goc` / `goc --ready` (table)** | **nothing** |

So the table view is the one surface where "the query ran and matched
nothing" is unrepresentable. Worse, it is unrepresentable *uniformly*:
a legitimately drained queue, a status filter matching no card, and a
mistyped `--worker` value are byte-identical blanks.

That last case is not reachable by the input-validation route the
sibling cards took. `--status` and `--tag` were both taught to reject
unknown values ([invalid-status-filter-silently-empties-queue](../invalid-status-filter-silently-empties-queue/),
[invalid-tag-filter-silently-empties-queue](../invalid-tag-filter-silently-empties-queue/)),
and the meta-fix
[query-flag-validation-is-opt-in-per-flag-and-new-flags-keep-missing-it](../query-flag-validation-is-opt-in-per-flag-and-new-flags-keep-missing-it/)
proposes one declared contract per query flag. `--worker` cannot join
that scheme: AGENTS.md defines the field as deliberately unregistered
("The value is unregistered — use a person slug, a machine name, or a
capability tag"), so there is no enum to validate against. For
`--worker`, an empty-result message is the *only* available signal —
which is why this card is the output-side complement of that family,
not a fourth instance of it.

## Empirical evidence

`uv run python .game-of-cards/deck/empty-queue-view-prints-nothing-instead-of-saying-no-cards-match/reproduce.py`
on a scratch deck whose three open cards are all gate-parked:

```
zero-match query → what the reader sees

  exit 0     0 bytes  table  `goc --ready`                       (nothing)
  exit 0     0 bytes  table  `goc --status disproved`            (nothing)
  exit 0     0 bytes  table  `goc --ready --worker typo`         (nothing)
  exit 0     3 bytes  json   `goc --json --ready`                '[]'
  exit 0   272 bytes  board  `goc --board --status disproved`    'OPEN                 | ACTIVE               | BLOCKED     '
  exit 0    31 bytes  triage `goc triage --worker typo`          'No parked cards (gate ≠ none).'

  the three table probes are byte-identical: True

3 table view(s) reported an empty result with no output.
FAIL: the table path stays silent while `triage` prints a sentence, `--json` prints [] and `--board` prints its header.
```

## Why it matters

The reachability path is this repo's own daily operation, not a
contrived input. `Skill(pull-card)` and `Skill(next-card)` both embed
the table view in their skill bodies as the sole queue evidence the
agent gets:

```
!`b=.claude/skills/_goc-bootstrap.sh; if [ -f $b ]; then sh $b --ready -v; else goc --ready -v; fi 2>&1 | head -22`
```

(`goc/templates/skills/pull-card/SKILL.md:42`; `next-card/SKILL.md:19`
is the same shape with `2>&1 || true`.) On this repo's live deck —
157 open cards at `human_gate: decision`, 16 at `session`, and the
only three at `none` all carrying a `waiting_on` overlay — that
injection renders as the `ACTIVE:` banner followed by nothing. The
skill then instructs the reader to "Pick the highest-contribution
**ready** card" from a blank region and to read a leverage line that
is also suppressed.

Both injections route stderr into stdout and discard the exit code
(`2>&1 | head -22`, `2>&1 || true`), so a reader cannot fall back on
either channel to tell the states apart. Establishing that the queue
was genuinely empty rather than mis-queried took three further
commands in a live 2026-08-04 pull-card session.

Distinct from [ready-leverage-line-goes-silent-when-no-card-is-pullable](../ready-leverage-line-goes-silent-when-no-card-is-pullable/),
which is about the *advisory* line `render_leverage_line` suppresses
when `ready` is empty. That card restores the Andon-cord ping; this
one restores the statement that the query matched nothing at all, and
covers every zero-match query, not just `--ready`.

## Fix

Give the table arm of `_cmd_default` (`goc/engine.py:3944-3951`) an
explicit empty-result line, following `_cmd_triage`'s precedent
verbatim — plain sentence, stdout, non-JSON path only:

- `render_table` keeps returning `""`; the message belongs to the
  command, not the renderer, so `--board` and `--json` are untouched
  and machine consumers of `--json` see no change.
- Name the filters that were in effect, so the `--worker`-typo case
  reads differently from a genuinely drained queue.
- Emit it whenever the filtered set is empty, independently of the
  active-card notice: that notice describes *other* cards, so it
  cannot stand in for the statement that this query matched nothing.

## Sibling sweep

`render_board` and `render_json` were checked and need no change:
`--json` emits `[]` and `--board` emits its header row, so both
already distinguish "ran, matched nothing" from "did not run".
`_cmd_triage` is the precedent being copied. No fourth site exists —
`_cmd_show` and `_cmd_validate` do not render filtered sets.
